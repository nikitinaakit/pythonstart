# Протокол фінальної командної ретроспективи проєкту «PythonStart»

## 1. Загальні відомості та підсумкові метрики проєкту
- **Команда проєкту:** Команда розробників «PythonStart» (Учасники 1–4)
- **Охоплений період:** Лабораторні роботи № 1 – № 15 (повний життєвий цикл SDLC від ідеї до релізу `v1.0.0`)
- **Фінальний статус MVP v1.0.0:** 100 % запланованих історій користувачів (`US-01` – `US-06`) виконано та розгорнуто у Production на GitHub Pages.
- **Ключові інженерні показники команди:**
  - реалізовано навчальних тем у тренажері: **4 теми** («Змінні», «Умови», «Цикли», «Списки»);
  - створено та успішно злито запитів на злиття (Pull Requests із Code Review): **понад 20 PR**;
  - покриття автоматизованими модульними тестами (Vitest): **4 тестові файли (понад 30 автотестів – 100 % Passed)**;
  - виявлено та усунено дефектів під час внутрішнього QA-аудиту (ЛР № 12): **4 дефекти (BUG-01...BUG-04)**.

## 2. Аналіз командної взаємодії за моделлю «Start, Stop, Continue»

### CONTINUE (Продовжити робити – наші найсильніші практики)
1. **Робота через ізольовані гілки (Feature Branch Workflow) та обов’язкове Code Review:** розподіл окремих файлів між учасниками (окремо `data/`, окремо `js/`, окремо `css/` і `docs/`) дозволив команді працювати паралельно без взаємного перезаписування коду.
2. **Автоматичний контроль якості перед злиттям (`npm run ci:check` та GitHub Actions):** запровадження скрипту лінтера і модульних тестів Vitest у ЛР № 11–13 повністю захистило головну гілку `main` від випадкових синтаксичних помилок.
3. **Критична верифікація згенерованого ШІ коду та ведення `AI Usage Log`:** правило «довіряй, але перевіряй» уберегло проєкт від XSS-вразливостей (`innerHTML`) та логічних хиб під час рефакторингу валідатора у ЛР № 10.
4. **Єдина візуальна дизайн-система у Penpot:** попереднє макетування у ЛР № 5 зі змінними кольорів (`--color-primary`) зекономило час під час верстання CSS у ЛР № 7.

### STOP (Припинити робити – що заважало або затримувало команду)
1. **Затримки під час очікування перехресного Code Review:** на перших етапах (ЛР № 6–7) окремі Pull Requests чекали на перевірку рецензента по кілька годин, що блокувало фінальне злиття.
2. **Використання абсолютних шляхів зі слешем на початку без думки про деплой:** на етапі локальної розробки у Live Server ми не відразу врахували, що на GitHub Pages проєкт працюватиме у підпапці `/pythonstart/`, тому перед ЛР № 14 довелося проводити аудит шляхів `./`.
3. **Нерівномірний темп комітів:** іноді учасники намагалися зробити всі зміни одним великим комітом наприкінці заняття замість дрібних покрокових фіксацій.

### START (Почати робити – що ми впровадимо у наступних проєктах)
1. **Підхід Test-Driven Development (TDD – написання тестів на старті розробки логіки):** писати модульні тести Vitest одночасно зі створенням функцій у ЛР № 8, а не чекати окремого етапу тестування у ЛР № 11.
2. **Регламент швидкого відгуку на Pull Request (SLA до 15 хвилин під час спільної роботи):** домовлятися у командному чаті про миттєве взаємне рецензування одразу після відкриття PR.
3. **Раннє підключення GitHub Pages (ще з етапу верстки у ЛР № 7):** вмикати публікацію на GitHub Pages одразу після появи `index.html`, щоб бачити реальну поведінку сайту в Production після кожного спринту.

## 4. Індивідуальна рефлексія та особистий внесок учасників команди
- **Учасник 1 (Координатор / Архітектор):** опанував адміністрування репозиторію GitHub, проектування модульної архітектури ES6, налаштування конвеєра CI/CD у GitHub Actions (`.github/workflows/ci.yml`), випуск релізу `v1.0.0` та публікацію на GitHub Pages.
- **Учасник 2 (Аналітик вимог / Педагогічний дизайнер):** навчився формулювати User Stories та критерії прийнятності за MoSCoW, структурувати навчальні дані у `data/topics.js`, проектувати розумну діагностику помилок учня та укладати користувацьку документацію `docs/user-guide.md`.
- **Учасник 3 (Дизайнер інтерфейсу / Frontend-розробник):** здобув навички прототипування у Penpot, адаптивного верстання на CSS3 Flexbox/Grid, створення каталогу тем із живим пошуком і фільтрацією (`js/topics.js`), локалізації інтерфейсу (`js/i18n.js`) та ведення журналу `CHANGELOG.md`.
- **Учасник 4 (Інженер із якості QA / Методист):** опанував розробку модуля збереження стану в `localStorage` (`js/storage.js`), інтеграцію асинхронного Fetch API з резервним Fallback (`js/api.js`), написання модульних тестів Vitest, оформлення Bug Reports та проведення післярелізного Smoke Testing.
